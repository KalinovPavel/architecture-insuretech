### Комментарии к новому сервису `osago-aggregator`

1. **Собственное хранилище** (`osago-aggregator-db`):  
   - Нужен для временного (или постоянного) хранения заявок на ОСАГО, статусов отдельных страховых компаний, результатов андеррайтинга.  
   - При 60-секундном SLA и большом числе параллельных заявок (до 2.5 тыс. одновременных клиентов), сервис должен масштабироваться и поддерживать хранение состояний.

2. **API для `core-app`**:  
   - **REST**: например, методы `POST /osago-requests` (создать заявку, возвращает ID), `GET /osago-requests/{id}` (получить частичные/итоговые предложения от страховых).  
   - `core-app` может периодически «дёргать» `GET` для получения свежих данных
   - (Опционально) Как вариант, можно сделать: `osago-aggregator` сам публикует события о частичных/готовых результатах.  

3. **Интеграция с `core-app`**:  
   - `core-app` синхронно ожидает предложения, либо показывает пользователю частичный ответ (websocket).
   -  (Опционально) Можно добавить «событийную» модель (если хотим, чтобы `osago-aggregator` публиковал событие `OsagoOfferUpdated`).   

4. **API для веб-приложения**:  
   - По-прежнему HTTP/REST (соответственно, `webApp` вызывает `core-app`),  
   - При необходимости мгновенной инкрементальной загрузки можно дополнить **WebSocket** между `webApp` и `coreApp`.  

5. **Паттерны отказоустойчивости**:  
   - **Circuit Breaker** и **Timeout** на вызовах `core-app` ↔ `osago-aggregator` и `osago-aggregator` ↔ `insuranceSystems`, поскольку внешние страховые системы могут отвечать долго или быть недоступны.  
   - **Retry** может применяться внутри `osago-aggregator` при запросах статуса страховых компаний.  
   - **Rate Limiting** также может пригодиться, если опасаемся перегрузить внешние API.  

6. **Масштабирование**:  
   - Все сервисы (включая `osago-aggregator`) могут быть развёрнуты в **нескольких экземплярах** за балансировщиком/Ingress/Kubernetes Service.  
   - `osago-aggregator-db` должен быть единым (или кластерным) для хранения общих состояний заявки.  
   - При правильной архитектуре сервис не зависит жёстко от числа экземпляров — важно поддерживать согласованность (через общую БД).

### Комментарии к диаграмме:  

1) У `osago-aggregator` появилось **собственное хранилище** (небольшая БД) для хранения состояний заявок ОСАГО и временных результатов.  
2) **API** сервиса `osago-aggregator` для `core-app` — синхронный *REST* (для начала), чтобы `core-app` мог создать заявку, затем запустить опрос решений.  
3) **Интеграция** между `core-app` и `osago-aggregator` — **REST** (или gRPC) плюс *Circuit Breaker / Retry / Timeouts*, так как запросы могут быть длительными.  
4) **API** для веб-приложения в `core-app` — по-прежнему *REST* (также можно добавить **WebSocket** для «мгновенной» отправки частичных результатов, если необходимо мгновенное обновление UI).  
5) Между веб-приложением и `core-app` остаётся *REST* (можно упомянуть, что возможен **WebSocket** канал для постепенной доставки результатов).  
6) В `osago-aggregator` и `core-app` (и др. сервисах) можно применять **Rate Limiting** и **Timeout** при вызовах во внешние страховые компании, а также **Circuit Breaker** для API `osago-aggregator` ↔ `insuranceSystems`.  
7) Все сервисы **развёрнуты в нескольких экземплярах** (скейлинг). Balancer (или Kubernetes Service) распределяет трафик между ними. Паттерны отказоустойчивости не зависят напрямую от числа экземпляров, но Circuit Breaker/Retry/Timeout крайне полезны для вызовов, которые потенциально могут зависать (60 секунд SLA).
